# Projects and Workspaces Implementation Plan (step 6b)

> **For agentic workers:** REQUIRED SUB-SKILL: use subagent-driven-development (recommended) or executing-plans to carry out this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

> **Two decisions, made by the user 2026-10-02 as recommended** (the spec's [Decided after the checks](../specs/projects-workspaces.md#decided-after-the-checks)):
> 1. **Setup runs outside the sandbox only on code a human merged** (a fresh clone, a clean checkout on `origin/<default>`, a worktree whose base is on `origin/<default>`). Elsewhere it is skipped and the answer says so (Tasks 6, 7a, 8).
> 2. **Both GitHub Apps are created read-only for now** (Contents, Pull requests and Metadata read). The code only ever asks for read tokens either way; only the rollout's App settings change.

**Goal:** Build what the [projects and workspaces spec](../specs/projects-workspaces.md) describes:
- `dish-projects`: the registry (`projects.yaml` in the config store), onboarding driven one project at a time, and **Settings → Projects**;
- `dish-workspaces`: clones under the work root, the GitHub App (JWT, read tokens, the credential helper), setup, workspace registration, the scratch workspace, task worktrees, the sweep, the `worktree` tool, and the **GitHub App** settings card;
- crew's `delegate` binding a coder to a worktree, with the brief block and `ChildRecord.worktree`;
- the shipped skills using the tool;
- then, with you, the Apps and the rollout.

**Architecture:**
- **Two plugins, one direction.** `dish-workspaces` depends on `dish-projects` (for the `Project` type and its events); `dish-projects` reads `dishWorkspaces` with `ctx.get` to drive onboarding and fill its page. Neither waits for the other at load.
- **dish-projects** claims `projects.yaml` (agent policy `propose`), seeds it empty, parses and validates it, keeps each project's onboarding status in its state directory, and runs one onboarding at a time in the background. It emits `dish-projects/changed` and `dish-projects/status`.
- **dish-workspaces** does the mechanics, through small modules with injected dependencies:
  - `git.ts` runs every git command dish makes (hooks and fsmonitor off, a scrubbed environment, its own process group, a time limit); `safety.ts` checks a clone before dish works in it;
  - `github.ts` is the App client (`node:crypto` RS256, `fetch`); `tokens.ts` mints read tokens into per-owner files for the helper and keeps a second, in-memory token for dish's own API reads;
  - `bin/git-credential-dish` is the `sh` helper each clone's config names;
  - `setup.ts` runs `setup` unsandboxed (merged code only), `clone.ts` and `onboard.ts` do steps 1 to 4, `registry.ts` and `scratch.ts` talk to dsh's workspace registry, `worktrees.ts` and `sweep.ts` own `.worktrees/`;
  - `service.ts` composes them behind a per-project lock, with the hourly round and the token timers; `tool.ts` is the `worktree` tool.
- **Crew** gains `worktree` on `delegate`, `ChildRecord.worktree`, the brief block, and `worktreeBindings(path)` for the sweep and `remove`.

**Tech Stack:** TypeScript run by Node 24's type stripping (erasable syntax only), `node --test`, Cordis, dsh 0.2.0-rc.2 (`dsh-workspace`, `dsh-credentials`, `dsh-tools`, `dsh-typert-protocol`; `dsh-storage*`, `dsh-session*` and `dsh-subprocess` in tests), git 2.47 (`git http-backend` in tests), POSIX `sh` (the helper, `shellcheck`), `js-yaml`, React 18 (clients, bundled by dish-kit's esbuild script).

## Global Constraints

- **Safety, for every implementer.** It is not negotiable.
  - **Never run against real state.** dsh, `pnpm dsh`, `pnpm dev` and `deploy/install.sh` never run against the real `~/.dsh`, `~/.config/dish`, `~/.local/state/dish`, `~/.local/share/dish`, `~/.cache/dish`, `~/work`, or the VM.
  - **Live runs use scratch directories:** `HOME`, `DSH_HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`, `DSH_DISH_HOME` and `TMPDIR` all scratch, and `pnpm_config_store_dir` set to what `pnpm store path` prints in your normal shell (6a's checks: another store aborts installs).
  - **Every process a test or a live run spawns gets a scratch `HOME`,** and an interactive shell a scratch `HISTFILE` (6a's notes: bash once saved its history over the real one). git reads `~/.gitconfig`: tests give every git they start a temp `HOME` (with a `.gitconfig` holding a test identity) and `GIT_CONFIG_NOSYSTEM=1`, and give the code under test a temp `HOME` through `process.env` (`withEnv`). `childEnvironment` drops every `GIT_*` name, so a test can't steer dish's own git with `GIT_CONFIG_GLOBAL` and the like.
  - **No network.** No test reaches GitHub or any other host: fake servers bind `127.0.0.1:0`, remotes are local bare repos (`file://`) or the fake smart-HTTP server. No live run calls GitHub's API with credentials, and none are created.
  - **Don't read `.envrc`,** and don't run `env` or `printenv`. Check whether a variable is set with `[ -n "${NAME+x}" ]`.
  - **The VM, incus, ansible and `~/projects/fleet` are off limits.** The rollout is the user's.
- **Check exit codes.** Never pipe the gate through `tail` or `head`.
- **Branch `projects`.** Task worktrees are cut from it. Humans merge.
- **Repo conventions** (as in the skills and ops plans):
  - Node 24, erasable TypeScript, no build step for server code. Tests in `<package>/test/*.test.ts`, run by the root `pnpm test`.
  - `@deepseek-ai/*` runtime imports only from packages declared under both `peerDependencies` (`^0.2.0-rc.2`, cordis `~4.0.4`) and `devDependencies` (`0.2.0-rc.2`). Everything else is `import type`.
  - Services a plugin doesn't `inject` (siblings: `dishConfig`, `dishProjects`, `dishWorkspaces`, `dishCrew`, `credentials`, `agents`) are read with `ctx.get(name)` on each use, never by property. Services that start later and are optional (`workspaceRegistry`, `tools`, `dishConfig` for the claim) are waited for with `ctx.inject([...], …)`.
  - Each plugin logs as its name, and prints its own lines with dish-kit's `printOwnLogs` when its `terminal` row is true.
  - Every task ends with `pnpm typecheck && pnpm test` passing (the gate), and one commit.
  - Shell scripts pass `shellcheck` (on `PATH` through brew).
- **The store-pin contract doesn't change.** No `storeDir` in `pnpm-workspace.yaml`, no store in `.npmrc`, and no store or `XDG_*` variable set by anything in this step.
- **Secrets.**
  - A token or the App key is never printed, logged, put in an error message, written to the config store, or written anywhere on disk but the token file (tokens) and dsh's credential store (the key, written by dsh). Every error text that could carry one (git's stderr, a response body, setup's output) goes through dish-kit's `maskSecrets` and is cut short.
  - A token never goes in an argument, a URL, an environment variable or a git config value: git gets it from the credential helper, which reads the token file.
  - The App ID and key are read with `ctx.get('credentials')?.resolve(ref)` for each use and dropped after it; never cached past one operation.
  - **Read-only in 6b.** `GitHubApp.createToken` accepts only `read` permissions and throws before any request otherwise. No code in this step makes a write token.
- **dish's own git.** Every git command dish runs goes through `git()` in `plugins/workspaces/src/git.ts` (no other `spawn('git', …)` in the package). Before dish works in a clone, `checkClone` passes. Never `--force` a worktree removal except through the tool's `force`.
- **Never delete what dish didn't make.** The only directories dish removes are its own temporary clone directory (on a failed clone) and worktrees it made (through `git worktree remove`); the only files, its own state files and token files. Removing a project deletes nothing on disk.
- **Paths are compared canonically** (`realpath`), and a path from outside (a tool argument, a record) is checked to be inside the clone before use.

## Review Focus

1. **A token reaches the disk anywhere but its file, or reaches a log.** Grep the diff for `token` in every log call, error, `JSON.stringify` and file write. Tests assert: no `ghs_` in any clone's `.git/config`, in `setup.log`, in `clone.json`, in logged lines or in an error a failing API call throws; the clone command passes no token in its argv or URL; `~/.git-credentials` isn't written even with `credential.helper=store` in the global config (Tasks 3b, 4, 7a).
2. **Push possible from an agent.** File tokens are minted with `contents: read` only, and `createToken` refuses anything else (Task 4). The helper answers only `get` for the configured web origin (Task 3b). The fake smart-HTTP server refuses `git-receive-pack` for a read token, and a test pushes and expects 403.
3. **The helper path breaking after an update.** The helper is invoked by absolute path through `/bin/sh` (no exec bit needed), the path is computed from the plugin's own real path, and `prepare` rewrites it at every start (Tasks 7a, 9). Dev's clones point at the dev checkout and dev's token directory.
4. **Onboarding touching a directory it didn't create or adopt.** An existing path that isn't the right clone is refused and left byte-for-byte as it was (test compares a listing before and after); a failed clone removes only its own temporary directory; nothing is ever `rm -rf`'d by name from outside (Task 7a).
5. **The sweep removing a dirty or bound worktree, or one with unpushed work.** The merged rule: tip-based PR lookup (`head.sha === tip`) or ancestry with commits of its own. A new worktree, a branch with commits after its PR merged, a dirty one, one bound to a running coder, one resolved in the last 5 minutes, and one dish didn't make are all kept (Task 8).
6. **Setup leaking the environment, or running agent-written code unsandboxed.** `childEnvironment` drops credential-shaped, `DSH_*` and `GIT_*` names (pinned to dsh's own pattern); setup runs only on merged code; a timeout or abort kills the whole process group (Task 6).
7. **dish's own git running agent-controlled programs.** A planted hook, `core.fsmonitor`, filter, `include.path` or `extensions.worktreeConfig` never runs or is refused; `git()` is the only way the package runs git (Tasks 3a, 7a, 8).
8. **Dev and prod crossing.** The work root, state and token files follow `DSH_DISH_HOME`; credentials follow `DSH_HOME`; nothing is cloned under `<home>/work` in dev (Tasks 1, 9). The dev App is separate (rollout).
9. **The scratch workspace coming back after removal.** It is registered once, recorded, adopted if already there, and not registered again once removed; deleting the record brings it back (Task 7b).
10. **Races between onboarding, fetch, sweep, `create` and `delegate`.** One per-project lock in the service; one onboarding at a time; removal of a project aborts its onboarding; token files written atomically; the recent-resolve guard (Tasks 9, 10).
11. **The main agent only.** `worktree` refuses non-top-level callers and is on crew's never-list; `delegate` binds only writing roles, only worktrees inside the chat's workspace, never one bound to a running child (Tasks 5, 9).

## Task 2: the registry format (`dish-projects`)

**Needs:** Task 0.

**Files:** create `plugins/projects/src/registry.ts`; test `plugins/projects/test/registry.test.ts`.

**Interfaces (`src/registry.ts`):**
```ts
export const PROJECTS_PATH = 'projects.yaml'
export const SEED_TEXT = 'projects: {}\n'
export const RESERVED_OWNERS: readonly string[]          // ['scratch']
export const OWNER: RegExp     // GitHub: 1–39 of [A-Za-z0-9-], no leading, trailing or doubled '-'
export const REPO: RegExp      // 1–100 of [A-Za-z0-9._-]; '.', '..' and names ending in '.git' are refused separately
export const SECRET_NAME: RegExp                          // /KEY|PASSWORD|SECRET|TOKEN/i, dsh's scrub
export const GATE_TIMEOUT = { min: 10_000, max: 600_000 } as const
export const SETUP_TIMEOUT = { min: 10_000, max: 3_600_000, fallback: '15m' } as const
/** '<n>s' | '<n>m' | '<n>h' (n a positive integer, no spaces) → ms; anything else undefined. */
export function parseDuration(text: string): number | undefined
export interface ProjectFields {                          // as written in projects.yaml
  family: string, role: string, gate: string, gateTimeout: string
  setup?: string, setupTimeout?: string, gateEnv?: Record<string, string>
}
export interface Project {
  name: string                    // the key, as written: "owner/repo"
  owner: string, repo: string
  family: string, role: string
  gate: string, gateTimeout: string, gateTimeoutMs: number
  setup: string | undefined, setupTimeout: string, setupTimeoutMs: number   // setupTimeout falls back to '15m'
  gateEnv: Record<string, string>                                             // {} when absent
}
export type ParseResult = { ok: true, projects: Project[], fields: Record<string, ProjectFields> } | { ok: false, problem: string }
export function parseProjects(text: string): ParseResult                     // projects sorted by name, case-insensitively
export function nameProblem(name: string): string | undefined
export function fieldsProblem(name: string, fields: unknown): string | undefined
export function serializeProjects(fields: Readonly<Record<string, ProjectFields>>): string  // keys sorted; fields in the order above; optional ones only when set
export function validate(path: string, text: string): string | undefined     // parseProjects' problem
export function namespaceSpec(owner: string): NamespaceSpec                  // { prefix: 'projects.yaml', owner, agent: 'propose', validate }
```

**Rules** (the spec's "Validation", exactly):
- YAML through `js-yaml`'s `load` with `JSON_SCHEMA`; the document must be a mapping whose only key is `projects`, itself a mapping (an empty one, `{}`, is valid; `projects:` with nothing is too, as `{}`).
- Keys: `nameProblem`; `scratch` as owner refused, compared case-insensitively; two keys equal case-insensitively refused.
- Each value a mapping with only the known fields. `family`, `role`, `gate`: strings, non-blank after trimming, single-line. `gateTimeout`: required, a duration in `GATE_TIMEOUT`. `setup`: optional, non-blank string. `setupTimeout`: optional, a duration in `SETUP_TIMEOUT`.
- `gateEnv`: optional mapping; names match `^[A-Za-z_][A-Za-z0-9_]*$`, none starting with `DSH_` (case-insensitive) or matching `SECRET_NAME`; values strings without a newline.

## Risks to watch

- **Setup is skipped on unmerged bases** (recommendation 1), so a task worktree cut from a plan branch has no `node_modules` until the agent installs. Inside the sandbox, pnpm writing the account's store needs approval (the main agent asks you; a coder needs the judge). 6c's sandboxed runner, with caches in the clone, is the fix; until then the skill tells the agent to run the command the tool gives.
- **The App key is readable by agents** (recommendation 2: read-only Apps). Step 7 must not add write before deciding how to keep the key from agents.
- **An agent's change to a clone's `.git/config` stops dish there.** The safety check refuses a key outside the allowlist, so the project fails at the next start or fetch until the key is removed. That is by design; the message names the key.
- **Agents' git and dish's fetch share a clone.** A fetch can meet a lock an agent holds (`index.lock`, a ref lock). It fails, is logged once, and the next round retries.
- **GitHub's commit-to-pull-request listing** is relied on for squash merges (documented behaviour, checked in the docs, not live). The rollout's checks include a squash-merged PR, so a surprise shows there.
- **App names are global on GitHub.** "dish" is likely taken: the rollout uses names of your own (`bketelsen-dish`, `bketelsen-dish-dev`). The slug, not the name, is the bot's login.
- **A public App can be installed by anyone.** The prod App must be installable on `frostyard`, so it's "any account". A stranger's installation gives them nothing; the card lists it.
- **dsh's `create(path, title)`** may lose its title parameter in a later dsh (its README's dev note); `registerWorkspace` falls back to `setTitle`, and Task 7b's test covers both.
- **Token files after a crash.** A SIGKILL leaves the token files (read-only, an hour at most) until the next start prunes and rewrites them.
- **Existing clones under `~/work`** from 6a's deploy-key days with an alias host (`git@github-dish:…`) aren't adopted; onboarding names the origin, and you move the clone aside.
