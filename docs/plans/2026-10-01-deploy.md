# Plan: dish on its own VM (`deploy`)

**Goal:** Build what the [deploy spec](../specs/deploy.md) describes:
- dish's `deploy/` directory: a profile writer, an install script, a systemd user unit and a README;
- fleet's side: the restricted `dish` Incus project, the OpenTofu VM, the guest role, the nightly backup and the docs;
- then, with you, the live rollout: the VM, `tailscale serve`, the move of the config store, and the sign-ins.

**Architecture:**
- **dish (this repo):**
  - `deploy/profile.ts` writes dish's rows into a dsh profile's own patch file: the `dish-config` remote and identity, and the default preset. It keeps the other rows and the comments.
  - `deploy/install.sh` builds, links the five bundles into the `web` profile, and runs the writer.
  - `deploy/dish-web.service` runs `dsh web` on `127.0.0.1:3080` with the tailnet name as a trusted host.
- **fleet (`~/projects/fleet`):** it follows the nsl builder's split.
  - An Ansible bootstrap role creates the restricted `dish` project.
  - `tofu/minideb` owns the VM.
  - A gated guest role prepares the account, Node, pnpm, Tailscale, the deploy keys and the checkout, then runs `deploy/install.sh` and starts the unit.
  - A backup role captures the VM nightly, on the Coder backup's pattern.

**Tech:** bash, TypeScript run by Node 24 (type stripping), the `yaml` package (already in the lockfile), systemd user units, Ansible core 2.19, OpenTofu with the Incus provider, pytest for fleet's offline contracts, Tailscale.

## Global Constraints

- **Two repositories.**
  - **dish tasks** (D1–D4) work on a branch `deploy` cut from `main` in this repo. Humans merge.
  - **fleet tasks** (F1–F5) work on a branch `claude/dish-vm` in `~/projects/fleet` and end in a pull request.
- **fleet is live infrastructure.** Read its `README.md`, `AGENTS.md` and `docs/validation.md` before writing anything. Claude never runs a play, `tofu plan` or `tofu apply` against live hosts. Fleet tasks are verified offline only:
  - `pytest`;
  - `ansible-lint` (production profile);
  - `--syntax-check`;
  - `tofu fmt -check` and `tofu validate`.

  You, or Semaphore, apply after reviewing the check/diff and the plan output.
- **Follow fleet's patterns exactly.** The closest models are:
  - **nsl builder:** `ansible/roles/minideb_nsl_ci`, `ansible/roles/nsl_builder`, `tofu/minideb` and `docs/nsl-builder.md`;
  - **Coder backup:** `ansible/roles/minideb_coder_backup`.

  Copy their structure, their naming (`fleet_dish_*` variables), their gate assertions (an explicit `*_approved` flag and an exact target), their ownership markers (`user.fleet.owner`, `user.fleet.disposable`) and their tests.
- **Secrets never go in Git, task output, chat or files Claude writes.** They are the two deploy keys, the Tailscale auth key, the Copilot sign-in and the TypeSafe key.
  - Fleet takes the first three from Semaphore as environment variables, the way `FLEET_NSL_RUNNER_TOKEN` is taken: passed on stdin, with `no_log: true`.
  - Copilot and TypeSafe are entered on the VM's Settings pages by you.
- **Nothing touches your real desktop profile, store or `dsh web`** before Task L1. dish tests use scratch `DSH_HOME` and scratch `XDG_*` (the live6 pattern).
- **The dish repo's own conventions carry over:**
  - erasable TypeScript only;
  - tests in `<dir>/test/*.test.ts`, run by the root `pnpm test`;
  - `pnpm typecheck && pnpm test` passing at the end of each task, with one commit per task.
- **One pusher.** The VM must not start against `bketelsen/dish-config` while the desktop still pushes there. L1 orders the move.

## Review Focus

1. **No secret can leak.** Look for leaks through a task's output, a template, a file mode, the journal, a backup's manifest, or a test fixture.
2. **Idempotence.** A second run of `install.sh`, or of any play, changes nothing and restarts nothing.
3. **Least privilege.**
   - The `dish` account has no sudo.
   - The Incus project allows one VM.
   - The Semaphore identity is limited to the `dish` project.
   - Nothing listens on the VM's own address.
4. **Fail safe.**
   - A checkout that can't fast-forward fails the run.
   - A run without approval fails before it changes anything.
   - `tailscale up` never runs when the VM is already on the tailnet.
5. **The store has one pusher, and its history is never rewritten.**

### Task D2 [dish]: The profile writer

**Files:**
- Create: `deploy/profile.ts` and `deploy/test/profile.test.ts`.
- Modify:
  - the root `package.json`: `yaml` as a devDependency at the lockfile's 2.9.1, and `deploy/test/*.test.ts` in the `test` glob;
  - the root `tsconfig.json`: include `deploy`.

**Interface:** `node deploy/profile.ts --patch <path> --remote <url> --user-name <name> --user-email <email> [--preset dish]`, run as a CLI. It also exports `writeDishRows(text, options) → string` for tests.
- **The `dish-config` row** (`id: dish-config`):
  - Its `config` gets `remote`, `userName` and `userEmail` set.
  - Keys already in that row's config are kept. Only these three are written.
  - If the row isn't there, it is added with `name: dish-config`.
- **The preset row** (`id: agent-preset-registry`, `name: "@deepseek-ai/dsh-agent-preset-registry"`):
  - `config: { default: <the row's existing default, else 'standard'>, selectedDefault: <preset> }`.
  - A patch replaces the whole `config`, so `default` is always written.
- **Everything else is kept as it is:** other rows, comments, key order, `!!js` tags.
- **The file:** a missing file is created. The file is written atomically, with mode 0600, as dsh's config editor does. An unchanged result is not written.
- **Exit codes:** it exits 0 and prints `unchanged` or `updated`. On an unreadable or invalid file it exits non-zero without writing.

**Steps:**
- [ ] **Step 1: Write the failing tests.** They cover:
  - an empty or missing file;
  - a file with dsh's own rows (copy the shape of `~/.dsh/profiles/web/cordis.patch.yml`'s llm and settings rows, with no real values) kept byte for byte outside dish's rows;
  - an existing `dish-config` row with extra keys;
  - an existing preset row whose `default` is not `standard`;
  - idempotence, where a second run is `unchanged` and doesn't write;
  - comments and `!!js` kept;
  - mode 0600;
  - an invalid file refused.
- [ ] **Step 2: Run them.** They FAIL.
- [ ] **Step 3: Implement.**
- [ ] **Step 4: Verify.** PASS.
- [ ] **Step 5: Commit.** "deploy: the profile writer"

### Task D3 [dish]: The install script and the unit

**Files:**
- Create:
  - `deploy/install.sh`;
  - `deploy/dish-web.service`;
  - `deploy/test/install.test.ts` (an integration test, skipped unless `DISH_INSTALL_TEST=1`).

**`install.sh`** runs from the checkout's root as the account that runs dsh, with `set -euo pipefail`.

- **Inputs** come from the environment: `DISH_REMOTE`, `DISH_USER_NAME`, `DISH_USER_EMAIL`, and `DISH_PROFILE` (default `web`).
- **Steps:**
  1. `pnpm install --frozen-lockfile`, then `pnpm build`.
  2. If `$DSH_HOME/profiles/$DISH_PROFILE` (default `~/.dsh/…`) is missing, create it from dsh's default profile, as the live6 pattern does (`pnpm exec dsh --profile <name> --from-default-profile web --dump-config >/dev/null`).
  3. For copilot, config, prompts, crew and judge, in that order: `pnpm dsh plugin --profile <name> add ./plugins/<x>`, only when the profile's `package.json` doesn't already link it.
  4. `node deploy/profile.ts --patch <profile>/cordis.patch.yml …`.
  5. Print a summary of what changed. Print nothing secret: the remote URL is not secret.
- **Exit status:** non-zero on the first failure, with the failing step named.

**`dish-web.service`:**

```ini
[Unit]
Description=dsh web for dish
After=network-online.target

[Service]
WorkingDirectory=%h/dish
EnvironmentFile=%h/.config/dish/deploy.env
ExecStart=/usr/bin/env pnpm dsh web --host 127.0.0.1 --port 3080 --no-open --trusted-host ${DISH_TRUSTED_HOST}
Restart=on-failure
RestartSec=5

[Install]
WantedBy=default.target
```

- **`PATH`:** set it so the pinned Node and pnpm are found. D1 says where fleet installs them; use an `Environment=PATH=…` that fleet's role matches.
- **`deploy.env`** is written by fleet and holds only `DISH_TRUSTED_HOST=dish.<tailnet>.ts.net`.

**Steps:**
- [ ] **Step 1: The integration test.** It is run with `DISH_INSTALL_TEST=1` and a built tree:
  - Run `install.sh` twice against a scratch `DSH_HOME` and scratch `XDG_*`.
  - The second run reports no changes, and doesn't touch the patch file's mtime.
  - `--dump-config` shows the five dish bundles, the `dish-config` row's remote, and the preset row.
- [ ] **Step 2:** `systemd-analyze verify --user deploy/dish-web.service`. Allow the expected warning about the missing `EnvironmentFile`.
- [ ] **Step 3: Implement**, then run Steps 1–2.
- [ ] **Step 4: Commit.** "deploy: install script and the dsh web unit"

### Task F3 [fleet]: The guest

**Model:** `nsl_builder` and `minideb-nsl-builder.yml`, which discovers the guest through the trusted Incus host and checks the OpenTofu owner marker.

**Files:**
- `ansible/roles/dish_guest/` (defaults, tasks, templates, handlers);
- `ansible/playbooks/minideb-dish-guest.yml`;
- `tests/test_dish_guest.py`.

**What the role does:**
- **Packages:** those from D1's note, plus git, curl, ca-certificates and build-essential.
- **Node:** the official tarball at D1's version, checked by SHA-256 and unpacked under `/opt/node-<version>`. pnpm at the lockfile's version, pinned the same way. Both on the unit's `PATH`.
- **Tailscale:**
  - from Tailscale's Debian repository, with a pinned signing key;
  - `tailscale up --hostname=dish` only when `tailscale status` shows it isn't logged in;
  - the auth key from `FLEET_DISH_TAILSCALE_AUTHKEY`, on stdin, with `no_log`;
  - then `tailscale serve --bg --https=443 http://127.0.0.1:3080` when the current serve config differs.
- **The account:**
  - `dish` gets a shell, no sudo, and linger on.
  - Its home holds the checkout, `~/.dsh` and the XDG directories.
- **Deploy keys:**
  - `FLEET_DISH_REPO_KEY` (read-only, `bketelsen/dish`) and `FLEET_DISH_CONFIG_KEY` (read-write, `bketelsen/dish-config`) are written to `~dish/.ssh/` with mode 0600, on stdin, with `no_log`.
  - An SSH config defines the aliases `github-dish` and `github-dish-config`.
  - GitHub's published ed25519 host key goes in `known_hosts`.
- **The checkout:**
  - The first run clones from `git@github-dish:bketelsen/dish.git` into `~dish/dish`.
  - Later runs `git fetch` and `git merge --ff-only origin/main`. A non-fast-forward fails the run.
- **The install:** `deploy/install.sh` runs as `dish` with:
  - `DISH_REMOTE=git@github-dish-config:bketelsen/dish-config.git`;
  - `DISH_USER_NAME` and `DISH_USER_EMAIL` from inventory variables.
- **The unit:**
  - `~/.config/dish/deploy.env` gets `DISH_TRUSTED_HOST`, from an inventory variable holding your tailnet's name.
  - `dish-web.service` is linked from the checkout into `~/.config/systemd/user`, then enabled and started.
  - It restarts only when the checkout's HEAD, `deploy.env` or the unit changed.
- **Gating.** It is gated by `fleet_dish_approved`, and runs only on the OpenTofu-owned `dish` guest.

**Tests:** offline contracts:
- the gating;
- `no_log` on every secret task;
- file modes;
- the ff-only rule;
- the unit restart conditions;
- `tailscale up` only when logged out;
- no secret in any template or default.

**Verify:** pytest, ansible-lint, syntax check.
