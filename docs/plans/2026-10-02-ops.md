# Ops Implementation Plan (step 6a)

> **For agentic workers:** REQUIRED SUB-SKILL: use subagent-driven-development (recommended) or executing-plans to carry out this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build what the [ops spec](../specs/ops.md) describes:
- a dev configuration that is the default for everything but the VM's service, with its data in the checkout's `.dev/`;
- `pnpm dev`, which installs dish into a dev profile and serves it on `127.0.0.1:3090`;
- a unit that runs dsh directly, in `~/work`;
- `deploy/update.sh` and `deploy/url.sh`, run by you on the VM through `incus exec`;
- the Copilot first sign-in on a fresh profile;
- fleet's side, as a pull request: provisioning only, `install.env`, the apt wrapper and mise;
- then, with you, the rollout.

**Architecture:**
- **Dev and prod.**
  - `scripts/env.ts` is the launcher for root package scripts. It sets `DSH_HOME=<checkout>/.dev/dsh`, `DSH_DISH_HOME=<checkout>/.dev` and `DISH_ENV=dev`, unless `DISH_ENV=prod`.
  - dish-kit's `xdgPaths` puts all four of dish's directories under `DSH_DISH_HOME` when it is set.
  - dsh drops `DSH_*` names from agent shells, so none of this reaches an agent's commands.
  - The service is prod because it runs `node_modules/.bin/dsh` directly with the account's defaults. It never goes through the launcher.
- **Updates.**
  - `update.sh` runs as the checkout's owner and does what fleet's guest play used to: fast-forward or roll back, `install.sh`, copy the unit, restart when stale, wait, and stamp.
  - It reads `install.sh`'s inputs from `~/.config/dish/install.env`, which fleet writes and the unit doesn't load.
- **Fleet** keeps provisioning (account, Node, pnpm, Tailscale, keys, first clone, `deploy.env`) and gains `install.env`, `~/work`, a root-owned apt wrapper with a sudoers rule for it, and a pinned mise.
- **Copilot.** The existing sign-in panel also registers in the Models page's footer, shown while no `github-copilot` route exists.

**Tech Stack:** bash (`set -euo pipefail`, shellcheck), TypeScript run by Node 24's type stripping (erasable syntax only), `node --test`, git, systemd user units, pnpm 11.25, dsh 0.2.0-rc.2, React 18 (the Copilot client, bundled by dish-kit's esbuild script). Fleet: Ansible core 2.19, pytest and ansible-lint from fleet's venv.

**Spec:** [docs/specs/ops.md](../specs/ops.md). Read it first, including its **Checks** section: the plan argues from it. The spec was corrected by those checks before this plan, in commit `docs: ops spec follows the checks`. The [deploy plan](2026-10-01-deploy.md) and `deploy/test/install.test.ts` have the conventions for deploy scripts and their tests.

## Global Constraints

- **Safety, for every implementer.** It is not negotiable.
  - **Never run against real state.** dsh, `pnpm dsh`, `pnpm dev`, `deploy/install.sh`, `deploy/update.sh` and `deploy/url.sh` never run against the real `~/.dsh`, `~/.config/dish`, `~/.local/state/dish`, `~/.local/share/dish`, `~/.cache/dish` or the VM.
  - **Live runs use scratch directories.** Any live run sets `HOME`, `DSH_HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_DATA_HOME` and `XDG_CACHE_HOME` to scratch directories. It leaves `DSH_DISH_HOME` unset, or scratch.
    - The launcher puts dev data in `<worktree>/.dev`. A launcher bug still must not be able to reach the real directories, so launcher runs get the scratch environment too.
    - Set `pnpm_config_store_dir` to what `pnpm store path` prints in your normal shell. With a scratch `XDG_DATA_HOME`, pnpm would otherwise pick another store, and the worktree's next install with work to do would abort (`ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY`).
  - **Tests use temp directories.** `update.sh` and `url.sh` run in tests only with `HOME`, `getent`, `id`, `runuser`, `systemctl`, `journalctl` and `curl` stubbed into the test's temp directory.
  - **Don't read `.envrc`,** and don't run `env` or `printenv`. Check whether a variable is set with `[ -n "${NAME+x}" ]`.
  - **The VM is off limits** to Tasks 1–9. The rollout is yours.
  - **`~/projects/fleet` is live infrastructure.** Only Task 9 touches it, and only on its own branch. Never run `ansible-playbook`, `tofu plan`, `tofu apply` or anything against a live host. Fleet's pytest suite, which drives `ansible-playbook` against local throwaway fixtures, is the one exception.
- **Check exit codes.** Never pipe the gate through `tail` or `head`.
- **Branch `ops`.** Task worktrees are cut from it. Humans merge.
- **The rollout ordering constraint.** `ops` reaches `main` as one merge. The launcher-wrapped `pnpm dsh` (Task 2) and the unit that runs dsh directly (Task 4) must land together. With the old unit, `ExecStart=… pnpm dsh web` would start the VM on an empty dev store. Never cherry-pick Task 2 to `main` without Task 4.
- **Repo conventions:**
  - Node 24, erasable TypeScript run by type stripping. `scripts/*.ts` run as `node scripts/<name>.ts`, like `deploy/profile.ts`.
  - Tests in `<dir>/test/*.test.ts`, run by the root `pnpm test`.
  - Every task ends with `pnpm typecheck && pnpm test` passing (the gate), and one commit.
  - Bash scripts start with `#!/usr/bin/env bash` and `set -euo pipefail`, are committed executable (mode 100755), and pass `shellcheck` (it is on `PATH` through brew).
- **The store-pin contract doesn't change.** No `storeDir` in `pnpm-workspace.yaml`, no store in `.npmrc`, and no store or `XDG_*` variable set by the launcher, `pnpm dev` or `update.sh` (spec, Checks).
- **Contracts** shared between tasks and repos:

  | Name | Value |
  |---|---|
  | dev root | `<checkout>/.dev/` (git-ignored), mode 0700, with `dsh/`, `config/`, `state/`, `data/`, `cache/` |
  | dev dsh home | `<checkout>/.dev/dsh` |
  | `DSH_DISH_HOME` | Absolute only. When set, dish's directories are `<it>/{config,state,data,cache}/<app>`, ahead of `XDG_*`. Dev sets it to `<checkout>/.dev`. |
  | `DISH_ENV` | Unset, empty or `dev` means dev. `prod` passes the environment through. Anything else exits 2. |
  | ports | prod `127.0.0.1:3080`, dev `127.0.0.1:3090` |
  | the account | The owner of the checkout the script sits in (`dish` on the VM). Its home comes from `getent passwd`. |
  | `~/.config/dish/deploy.env` | Unchanged: one line, `DISH_TRUSTED_HOST=<host>`. The unit loads it. |
  | `~/.config/dish/install.env` | Written by fleet, mode 0600: `DISH_REMOTE=…`, `DISH_USER_NAME=…`, `DISH_USER_EMAIL=…`. One `NAME=value` per line; the value is the rest of the line, verbatim, with no quote processing. Blank lines and `#` lines are ignored. Each name appears exactly once. The unit never loads it. |
  | the stamp | `~/.local/state/dish/deploy/started`, six lines: `revision <sha>`, `unit <sha256>`, `deploy.env <sha256>`, `install.env <sha256>`, `node <node --version>`, `pnpm <pnpm --version>` |
  | the lock | `~/.local/state/dish/deploy/lock` (`flock`) |
  | the unit | `~/.config/systemd/user/dish-web.service`, copied from `deploy/dish-web.service` |
  | `~/work` | the service's working directory |
  | apt wrapper | `/usr/local/sbin/dish-apt-get` (fleet), with sudo for it alone |
  | mise | `/usr/local/bin/mise` (fleet), root-owned, pinned |

## Review Focus

1. **Prod is prod, and dev is dev.**
   - The unit runs the checkout's dsh binary, never `pnpm` or the launcher, and sets no `DISH_ENV` (Task 4's test).
   - The launcher defaults to dev and replaces an inherited `DSH_HOME` (Task 2's tests).
   - `pnpm dev` refuses `prod` and forces `DISH_REMOTE=''` (Task 3).
   - `install.sh`'s dsh commands never see `DSH_DISH_HOME` (Task 1's install test).
2. **Nothing of dev's or of the install's reaches an agent shell.**
   - The launcher adds exactly `DSH_HOME`, `DSH_DISH_HOME`, `DISH_ENV` and a `PATH` prefix, and no `XDG_*` or pnpm name (Task 2's key-set test).
   - The unit loads no install inputs (Task 4).
   - `deploy.env` stays one line (Task 9's test).
3. **`update.sh` never half-updates.**
   - Every refusal comes before the first change: a dirty or diverged checkout, another branch, an unknown ref, missing or empty inputs, the lock.
   - The stamp is written only after dsh answers.
   - It restarts exactly when stale, stopped, or when `install.sh` changed the profile.
   - `install.sh` runs in the unit's environment, with no `XDG_*`, `PNPM_HOME` or `DSH_*` (Task 5's tests).
4. **No token leaks.**
   - `update.sh` prints no line containing "token", in any case.
   - `url.sh` prints the token once, on stdout only, and never on stderr (Tasks 5 and 6).
5. **The apt rule is apt and nothing else.**
   - The wrapper refuses options, paths, version pins and empty lists.
   - The sudoers drop-in names only the wrapper, and the play checks `sudo -l` for exactly that (Task 9's tests).
6. **The Copilot first sign-in works on a fresh profile,** and the footer card goes away once the route exists (Task 7's tests, then the rollout's live check).

**Interfaces (`scripts/env.ts`):**
```ts
export type Mode = 'dev' | 'prod'
export class UsageError extends Error {}
/** The checkout this file belongs to (its parent directory), never process.cwd(). */
export const ROOT: string
/** DISH_ENV: unset, '' or 'dev' → 'dev'; 'prod' → 'prod'; anything else throws UsageError (exact match, case-sensitive). */
export function resolveMode(env: NodeJS.ProcessEnv): Mode
/** `env` plus exactly: DSH_HOME=<root>/.dev/dsh, DSH_DISH_HOME=<root>/.dev, DISH_ENV=dev, PATH=<root>/node_modules/.bin:<PATH>. Inherited values of those names are replaced. Nothing else is added, changed or removed. */
export function devEnvironment(root: string, env: NodeJS.ProcessEnv): NodeJS.ProcessEnv
/** dev → devEnvironment; prod → `env` with only the PATH prefix added. */
export function environmentFor(mode: Mode, root: string, env: NodeJS.ProcessEnv): NodeJS.ProcessEnv
/** Make <root>/.dev and dsh/, config/, state/, data/, cache/ under it, mode 0700 (chmod, since the umask only narrows). */
export function ensureDevDirectories(root: string): Promise<void>
/** `node scripts/env.ts <command> [args...]`. Returns the exit code: the command's, 128+n for a signal, 127 when it can't be started, 2 for usage. */
export function main(argv: string[], options?: { root?: string, env?: NodeJS.ProcessEnv }): Promise<number>
```

**Behavior:**
- **The command.** `main` spawns it with inherited stdio, in the current working directory, with `environmentFor(mode, root, env)`. In dev it calls `ensureDevDirectories` first.
- **Signals.** It forwards `SIGINT`, `SIGTERM` and `SIGHUP` to the child.
- **Usage errors** (no command, or a bad `DISH_ENV`) print one line to stderr and return 2 before anything else happens. The bad-value message is `env: DISH_ENV must be dev or prod (unset means dev), not "<value>"`.
- **The CLI tail:** `if (import.meta.main) process.exitCode = await main(process.argv.slice(2))`, as `deploy/profile.ts` does.

## Task 5: `deploy/update.sh`

**Files:**
- Create `deploy/update.sh` (mode 100755).
- Create `deploy/test/host.ts` and `deploy/test/update.test.ts`.

**CLI contract:**
```
deploy/update.sh [--apply] [<ref>]
  (no flags)   dry run toward origin/main
  <ref>        a commit or tag; with --apply, checked out detached (a rollback)
  -h, --help   usage on stdout, exit 0
Exit: 0 done or nothing to do; 1 a failed step, named on stderr as "update: FAILED at step: <step> (exit N)";
      2 usage (an unknown option, two refs, a ref starting with "-") or the wrong account.
Reads:  <home>/.config/dish/install.env, <home>/.config/dish/deploy.env, the checkout's deploy/dish-web.service.
Writes: <home>/.config/systemd/user/dish-web.service, <home>/work, <home>/.local/state/dish/deploy/{started,lock}.
Test-only knob: DISH_UPDATE_WAIT, seconds to wait for dsh (default 120).
```
stdout lines start with `update: `. The dry run prints, in order:
- `HEAD <sha> (<branch>|detached)`;
- `target <sha> (<ref or origin/main>)`;
- one of `N commits to apply`, `N commits to roll back`, `already at the target` or `diverged`, then the matching `git log --oneline` lines, indented two spaces;
- `unit: same|changes|not installed`;
- `deploy.env: …` and `install.env: …`, each `same as the last start`, `changed since the last start` or `no record of a start`;
- `restart: needed (<reasons>)` or `restart: not needed`;
- `dry run; run with --apply to update`.

After `--apply` it prints:
- `HEAD <sha>`;
- `dish-web.service: <is-active> (restarted|unchanged)`;
- the journal tail, under `journal (last 15 lines, token lines removed):`;
- when it restarted, `run deploy/url.sh for a fresh sign-in link`.

**Structure:**
- **One function.** The whole body is functions. The last line is `main "$@"; exit`.
- **The account and the checkout.** `self` is the script's resolved path, and the checkout is `self`'s `../`. The account is the checkout's owner (`stat -c %U`). Its uid and home come from `getent passwd <account>`. A checkout owned by root is refused (1).
- **The clean environment** is `env -i` with:
  - `HOME=<home>`, `USER` and `LOGNAME`;
  - `XDG_RUNTIME_DIR=/run/user/<uid>`;
  - `PATH=<the Environment=PATH= value of the checkout's unit>`; a unit without one fails (1);
  - `TMPDIR=/tmp`, `LANG=C.UTF-8` and `DISH_UPDATE_CLEAN=1`;
  - `DISH_UPDATE_WAIT`, if it is set.

  Nothing else, so no `XDG_*`, `PNPM_HOME`, `DSH_*` or `NODE_ENV`.
- **Who it runs as:**
  - **`id -u` is 0:** run `runuser -u <account> -- env -i <clean> DISH_UPDATE_PARENT=root bash <self> <args>` and keep its status. After an `--apply` run, as root, print the journal tail: `journalctl _UID=<uid> _SYSTEMD_USER_UNIT=dish-web.service -n 15 --no-pager -o short-iso`, minus every line matching `token` case-insensitively. Exit with the child's status.
  - **`id -un` is the account and `DISH_UPDATE_CLEAN` is unset:** `exec env -i <clean> bash <self> <args>`.
  - **The account with `DISH_UPDATE_CLEAN=1`:** do the work below.
  - **Anyone else:** `update: run update.sh as root or as <account>`, exit 2.
- **The work, as the account:**
  1. **The lock.** `mkdir -p ~/.local/state/dish/deploy`, then `flock -n` on `lock`. When it is busy, fail with "another update is running".
  2. **The inputs.**
     - `install.env`: exactly the three names, each once. `DISH_REMOTE`, `DISH_USER_NAME` and `DISH_USER_EMAIL` must be non-empty. An empty remote is refused: prod always pushes, and `install.sh` would remove the remote.
     - `deploy.env` must exist.

     The dry run checks these too, so a dry run that passes means `--apply` can start.
  3. **Fetch.** `GIT_TERMINAL_PROMPT=0 git -C <checkout> fetch --prune origin`.
  4. **The target:** `git rev-parse --verify --quiet --end-of-options "<ref>^{commit}"` for a ref (unknown: fail), else `origin/main`.
  5. **The report.** Relation, logs, the unit compared through `git show <target>:deploy/dish-web.service`, the env files against the stamp, and the restart decision the target would get. The dry run stops here, exit 0.
  6. **Refusals, before any change:**
     - `git status --porcelain --untracked-files=normal` not empty: "local changes", listing up to 10 paths. Ignored files, such as `node_modules` and `.dev/`, don't count.
     - With no ref: on another branch than `main` and not detached. Then, on `main`, `git merge --ff-only origin/main` must succeed. When detached, `git switch main` first.
     - With a ref: `git switch --detach <sha>`.
  7. **The install.** `DISH_REMOTE=… DISH_USER_NAME=… DISH_USER_EMAIL=… <checkout>/deploy/install.sh`, in the clean environment. Its output passes through, and its last line must be `install: profile changed` or `install: no changes to the profile`.
  8. **The unit.**
     - When it differs or is missing: `mkdir -p ~/.config/systemd/user`, copy it there (temp file, then `mv`, mode 0644), and `systemctl --user daemon-reload`.
     - `mkdir -p ~/work` (0700).
     - When `systemctl --user is-enabled dish-web.service` isn't `enabled`, `systemctl --user enable dish-web.service`.
  9. **Restart** with `systemctl --user restart dish-web.service` when any of these holds; the reasons are named on stdout:
     - `is-active` isn't `active`;
     - `install.sh` printed `profile changed`;
     - the stamp is missing;
     - a stamp line differs.
  10. **Wait,** always. Poll `curl -s -o /dev/null -w '%{http_code}' --max-time 2 http://127.0.0.1:3080/` every 2 seconds, up to `DISH_UPDATE_WAIT` (default 120). Any code but `000` means dsh answers. On a timeout, fail: "dsh did not answer on 127.0.0.1:3080 within N seconds". The stamp is untouched.
  11. **The stamp.** When it restarted, write it: a temp file, then `mv`.
  12. **Print** HEAD and the unit's state. When not run under `DISH_UPDATE_PARENT=root`, print the journal tail on a best-effort basis: `journalctl --user -u dish-web.service -n 15 --no-pager`, filtered the same way. When that fails, print `journal: not readable as <account>; run update.sh as root to see it`.
- **Failures.** A `begin <step>` helper and an `EXIT` trap name the failed step, as `install.sh` does.

## Risks to watch

- **The first update needs a hand fast-forward.** The VM's checkout predates `update.sh` (rollout step 3). Skipping it just means `update.sh` isn't there yet.
- **dsh loads `~/work/.env`.** An agent that writes one changes the service's environment at its next restart, for names dsh doesn't reserve. The docs say to keep `~/work` free of a `.env`. A guard is a non-goal.
- **`apt-get install` of any Debian package still runs maintainer scripts as root.** That is decision 7, and the wrapper only stops options and local files. Each install still needs your approval (or the judge's, for a child), because sudo can't work inside the sandbox.
- **mise's shims aren't on the unit's `PATH`.** Agents need `mise exec`. Changing that is step 6b's call.
- **A dsh upgrade could start reading some `DSH_DISH_HOME`.** That is unlikely, but the name sits in dsh's prefix on purpose, to get its scrub. If dsh ever reserves it, rename it in dish-kit and the launcher together.
- **The old desktop profile stays.** `~/.dsh/profiles/web` and `~/.config/dish` on the desktop are left alone. Remove them by hand.
