# Gates Implementation Plan (step 6c)

> **For agentic workers:** REQUIRED SUB-SKILL: use subagent-driven-development (recommended) or executing-plans to carry out this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

> **Two calls for you before the build starts** ([Spec corrections](#spec-corrections-for-the-user) 1 and 2). The plan is written with my recommendation for each, and says what changes if you choose otherwise:
> 1. **No cache redirects.** A gate runs with the environment the coder's own sandboxed shell has, plus the project's `gateEnv` (Task 5).
> 2. **The last round isn't steered back.** The failure that uses the last round ends the coder's turn, so every gate result is about the code as the coder left it (Task 6).

**Goal:** Build what the [gates spec](../specs/gates.md) describes, with the corrections below:
- `dish-gates`: a host-level `agent/turn-stopping` listener. When a crew coder bound to a worktree is about to end its turn, it runs the project's gate through dsh's sandboxed shell, records the result in crew's record, and steers a failure back to the coder, up to `maxRounds` per turn;
- crew: gate results in the record (`GateResult`), a gate line in the finish notice, the review check with `gateOverride`, and the gate sentence in the worktree brief;
- deploy and docs, a scratch end-to-end run, and then the rollout with you.

**Architecture:**
- **One new plugin, `dish-gates`.** It is a host plugin, like `dish-crew`'s host, so it hears every agent's `agent/turn-stopping` and `session/event`. It acts only for a crew child whose record names a worktree.
  - Nothing is injected: it reads `dishCrew`, `dishWorkspaces`, `dishProjects` and dsh's `shell` with `ctx.get` on each use.
  - It provides `dishGates`, with one method, `gateFor`.
- **Small modules with injected dependencies:**
  - `closing.ts`: the head of the closing message (from `session/event`), and the opt-out;
  - `text.ts`: the message to the coder;
  - `env.ts`, `logs.ts` and `run.ts`: one gate run over `ctx.shell`;
  - `listener.ts`: the spec's steps, the per-worktree lock, and rounds;
  - `index.ts`: the plugin.
- **Crew owns the record.** `GateResult` is crew's type. Results of the run in progress sit on `ChildRecord.gates`, and `endRun` files them on the run.
- **Crew reads `dishGates` structurally,** as it reads `dishWorkspaces`, and doesn't depend on `dish-gates`. The service being there says gates run, and `gateFor` gives the gate for the brief.
- **Nothing of 6b's code changes,** except one comment, and the docs that named 6c's runner and `.worktrees/.cache`.

**Tech Stack:**
- TypeScript run by Node 24's type stripping (erasable syntax only), `node --test`, Cordis;
- dsh 0.2.0-rc.2:
  - at runtime, `dsh-llm`'s `createUserMessage`;
  - for types, `dsh-agent`, `dsh-session`, `dsh-shell` and `dsh-sandbox`;
  - in tests, dsh's real shell stack: `dsh-subprocess-local`, `dsh-sandbox-local`, `dsh-session-projection`, `dsh-sandbox-policy` and `dsh-bash-sandbox`;
- bubblewrap (`/usr/bin/bwrap`) for the real-shell tests, and git 2.47 in test fixtures.

**Spec:** [docs/specs/gates.md](../specs/gates.md), approved 2026-10-02, with the corrections below. It builds on:
- 6b ([spec](../specs/projects-workspaces.md), and "What 6c builds on" in the [plan](2026-10-02-projects.md));
- [sandbox-home](../specs/sandbox-home.md);
- #10 (a worktree's setup runs in the sandbox) and #11 (the judge's read-only rule);
- the [friction fixes](../specs/friction.md).

Model the code on `plugins/crew` (record, notice, host listeners) and `plugins/workspaces` (injected dependencies, `test/helpers.ts`, real git fixtures).

**Decisions it relies on:**
- **The spec's decisions 1–7** (2026-10-02), as corrected below.
- **sandbox-home** (approved 2026-10-02, merged in #9). On the VM, an agent's sandboxed shell, and so a gate, writes the home directory, except a protected list.
- **6b's decision A and #10.** A worktree skips setup outside the sandbox (A), and its setup runs in the sandbox, by the main agent or the coder (#10).
- **The friction fixes.** A crew child reports once, in its closing message. The judge's task for a child is its brief and its latest instruction from its parent or a person.

## Spec corrections (for the user)

I checked each interface the spec names against `main` (`516f17a`) and dsh 0.2.0-rc.2's sources under `node_modules/.pnpm`. I also ran one scratch spike: dsh's shell stack composed in a test `Context`, with and without `deploy/dish-sandbox` as its runner.

Each item says what the spec says, what's true now, the change, and why. Items marked **needs your call** are decisions. Items marked **obvious** are applied in the plan.

1. **The gate's caches** (decision 4; "Running the gate", Caches). *Needs your call.*
   - **Spec:** everything outside the clone is read-only under the sandbox. So the gate gets `XDG_CACHE_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `GOPATH`, `npm_config_cache` and `CARGO_HOME` under `<clone>/.worktrees/.cache/`.
   - **True now:** a gate can write the home directory, as an agent's shell can.
     - `ctx.shell` is `dsh-bash-sandbox`. It confines through `dsh-sandbox-local`, whose `runnerCommand` on the VM is `deploy/dish-sandbox`.
     - The spike checked it: with the script as runner, `$HOME/.cache/go-build` was writable, and `~/.ssh/x` and `/usr/x` were refused with "Read-only file system".
   - **The redirects now do harm:**
     - `common.md` tells agents never to point `HOME`, `XDG_*` or `MISE_*` into the workspace.
     - `XDG_DATA_HOME` and `XDG_STATE_HOME` hide mise's installs and its trust records: fleet's toolchains and the trusted `~/work`.
     - pnpm works out another store, and then refuses an existing `node_modules` without a terminal (the ops spec's Checks).
     - Go downloads every module again for each clone.
     - A gate would run a command differently from the coder's own run of it.
   - **Change (recommended):** no cache variables.
     - The gate's environment is dsh's own, scrubbed as for an agent's shell, plus `gateEnv`.
     - A machine whose sandbox can't write the home directory is dev without `DISH_SANDBOX_HOME=on`. There, a project that needs a writable cache sets it in `gateEnv`, such as `GOCACHE: <clone>/.worktrees/.cache/go-build`. The README says so.
     - `.worktrees/.cache` is no longer 6c's.
   - **If you keep the spec:** Task 5's `gateEnvironment` puts the six variables under `<clone>/.worktrees/.cache/` before `gateEnv`, and its tests check them.

2. **The last round** (steps 4–6). *Needs your call.*
   - **Spec:** each failure is steered back to the coder, up to 3. The stop after the third failure isn't gated, so the turn closes with "failed, round 3".
   - **True:** the coder changes code after the third failure, and that change is never gated.
     - The notice then reports a failure of code that has changed since.
     - "Done means the gate actually passed" doesn't hold for it.
   - **Change (recommended, A):** the failure that uses the last round (`round === maxRounds`) is recorded and not steered: the turn ends with it.
     - That is at most `maxRounds` gate runs per turn, 30 minutes at worst.
     - Each result describes the code as the coder left it.
     - The coder gets two fix attempts per run.
     - Step 4 stays as a guard: another listener can still steer a turn on.
   - **Other options:**
     - **B:** the spec as written.
     - **C:** steer all three failures, and gate a fourth stop without steering it. That gives three fix attempts, and up to 40 minutes a turn.

3. **There is no "run in progress" in crew's record** (The record). *Obvious, applied.*
   - `ChildRecord.runs[]` gets an entry only when a run ends (`endRun`). So results of the run in progress go on `ChildRecord.gates`, and `endRun` moves them onto the new `RunRecord.gates`.
   - Rounds are counted per dsh turn (`agent/turn-stopping`'s `turn`).
     - A steer continues the turn.
     - A follow-up, or any message to a finished child, starts a new turn: see `turn()` in `dsh-agent-loop`. dsh-subagent cold-resumes a child only on a parent's message.
   - `GateResult` gains `turn`, `maxRounds`, `command`, `excerpt` and `reason`, which the notice and the refusal quote.
   - Logs are named `<child>-<turn>-<round>.log`.

4. **A bound coder whose worktree doesn't resolve** (step 1). *Obvious, applied.*
   - `dishWorkspaces.resolve` also gives `undefined` when the clone or the worktree fails dish's safety check. As written, a coder that put a refused key in `.git/config` would skip its gate silently.
   - With a worktree on the record:
     - `resolveProblem` gives a reason → `error`, with that reason;
     - no reason (the worktree was removed, or the project unregistered) → `skipped`, "not gated: …";
     - dish-workspaces missing, or no sandboxing shell → `error`.
   - None of these is steered. The notice and the review check can then say why.

5. **The review check** (Reviews). *Obvious, applied.*
   - **Only while dish-gates runs** (`ctx.get('dishGates')`). With gates off, every review of a bound coder would need a ruling.
   - **What counts as not passed**, as the spec reads it, refused unless `gateOverride`:
     - a bound coder that is still running;
     - a latest run with no gate result: an error or an abort before the turn ended, or a restart mid-gate.
   - **A re-review is a review.** The check applies to a follow-up to a reviewer too (`to`, which is how the skills re-review). `gateOverride` works there as well, and the ruling goes into the follow-up's text.
   - **The override's text:**
     - `gateOverride` is ignored when no check refuses: the gate passed, the coder is unbound, or `reviews: "main"`.
     - An empty string means none: models fill every optional parameter with `''`.
     - "A blank override" is one with no ruling in it, such as `Ruling:` alone. It is refused.
     - Line breaks are folded into one line, not refused.

6. **The brief's gate sentence needs the gate** (The worktree brief block). *Obvious, applied.*
   - `worktreeBrief` takes the gate as an optional second argument. Crew reads it from `dishGates.gateFor(project)`.
   - So the sentence appears only while dish-gates runs, and crew doesn't read dish-projects.
   - dish-gates provides that one-method service. The design doc's table gave it none.

7. **`gateEnv`'s validation is 6b's** (Caches). *Obvious.*
   - 6b's registry already validates it, with tests: names, `DSH_*`, secret-looking names, one line, no NUL (`plugins/projects/src/registry.ts`).
   - 6c only expands `<clone>` and `<worktree>` in the values.

8. **Running the gate: output, sandbox and timeout.** *Obvious, applied.*
   - **One stream of output.** dsh's executor collects stdout and stderr separately. `stdoutMaxBytes` applies to stdout only, and stderr keeps the executor's 64 KB. So the gate runs as `exec 2>&1`, then the project's command.
     - The output is then one stream, in order, within 4 MB.
     - A gate's own stderr can't be taken for a runner failure. dsh classifies `bwrap: ` and `dish-sandbox: ` on stderr as one.
     - A sandbox refusal is recognised by "Read-only file system" in the output, for a hint to the coder.
   - **Only a sandboxing shell.** The gate runs through `ctx.shell` only when it sandboxes, that is when `ctx.shell.sandboxMode` is set. `dsh-bash-local` ignores a policy and would run the gate unconfined.
   - **No unconfined retry.** When no runner works, dsh itself refuses to run unconfined (`SANDBOX_UNAVAILABLE`). That is an `error`, never a retry.
   - **The timeout.** The executor clamps `timeoutMs` to its `maxTimeoutMs`, 600 000 by default. The gate reports the limit that applied.
   - **Writes.**
     - On the VM a gate also writes the home directory (item 1).
     - In dev with `DISH_SANDBOX_HOME=on`, clones under `<checkout>/.dev/work` sit inside the protected checkout. They are read-only to every sandboxed command, a gate included: sandbox-home's known limit.
     - The spec's test "writes outside the clone are refused" becomes: writes outside the clone, the per-call `/tmp` and, with `dish-sandbox`, the home directory are refused, and so are writes to protected paths.
   - **Secrets.** The output's secrets are masked (dish-kit's `maskSecrets`) before it reaches the log, the record or the coder, as 6b does for setup. That isn't screening, which the spec rightly leaves out.

9. **The opt-out.** *Obvious, applied.*
   - The marker may follow Markdown marks (`**BLOCKED:**`, `# NEEDS CONTEXT:`), in any case, and `NEEDS_CONTEXT:` counts too.
   - A skip lets nothing through, since the review still needs a pass or a ruling. So a looser match only saves a gate run.

10. **The open items, answered.**
    1. **Past 10 minutes:** possible, not done.
       - `onExpiry: 'none'` arms no deadline, and dish could abort the gate at a deadline of its own.
       - The non-goal stands: a turn stays running for as long as its gate does.
    2. **The closing text:** a `session/event` listener.
       - dsh calls it synchronously inside the append, so the step's `assistant/message` is seen before `agent/turn-stopping`.
       - dsh's `turnOutline` projection has a `draft` preview, but only the web profile mounts it.
       - `snapshotEvents` is deprecated.
    3. **A restart mid-gate:** the gate dies with dsh, and nothing is recorded for it.
       - bwrap runs it with `--die-with-parent` and `--unshare-pid`, and the subprocess service kills its range at teardown.
       - dsh doesn't resume the child by itself. A message from the main agent cold-resumes it into a new turn, which is gated from round 1.
       - The run before has no gate result, so a review of it needs a ruling.

11. **Unchanged, checked.**
    - **#11 and the friction fixes don't touch the gate.**
      - The gate runs through `ctx.shell`, not a tool call, so the judge never sees it.
      - The steer (source `dish-gates`) is never part of the judge's task, which takes only a child's brief and its latest instruction from its parent or a person.
    - **The bundle list** gains `gates` (Task 8). The spec doesn't say so.
    - **Stale wording in 6b's docs.** `plugins/workspaces/README.md` and the 6b spec say "6c's sandboxed runner can take the install over". Since #10 the install already runs in the sandbox. Task 8 rewords them.

## Global Constraints

- **Safety, for every implementer.** It is not negotiable.
  - **Never run against real state.** dsh, `pnpm dsh`, `pnpm dev` and `deploy/install.sh` never run against the real `~/.dsh`, `~/.config/dish`, `~/.local/state/dish`, `~/.local/share/dish`, `~/.cache/dish`, `~/work`, or the VM.
  - **Live runs use scratch directories.**
    - `HOME`, `DSH_HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`, `DSH_DISH_HOME`, `TMPDIR` and `HISTFILE` are all scratch.
    - `pnpm_config_store_dir` is set to what `pnpm store path` prints in your normal shell (6a's checks: another store aborts installs).
  - **Every process a test spawns gets a scratch `HOME`.** `pnpm test`'s preload (`scripts/scratch-home.ts`) gives each test process its own `HOME` and `HISTFILE`, so run test files only through `pnpm test`.
  - **git in fixtures.** A test that runs git gives it a scratch `HOME` with a `.gitconfig` holding a test identity, and `GIT_CONFIG_NOSYSTEM=1`.
  - **The real-shell tests set more.** They set `XDG_*`, `DSH_HOME` and `DSH_DISH_HOME` to scratch in `process.env` (`withEnv`) before they compose dsh's stack: a gate's environment is dsh's own process environment, scrubbed.
  - **No network.** No test reaches a model, GitHub, TypeSafe or any other host. The end-to-end run's model is a scripted server on `127.0.0.1`.
  - **Don't read `.envrc`,** and don't run `env` or `printenv`. Check whether a variable is set with `[ -n "${NAME+x}" ]`.
  - **The VM, incus, ansible and `~/projects/fleet` are off limits.** The rollout is the user's.
- **Check exit codes.** Never pipe the gate through `tail` or `head`.
- **Branch `gates`.** Task worktrees are cut from it. Humans merge.
- **Repo conventions** (as in the projects and friction plans):
  - **Code.** Node 24, erasable TypeScript only: no `enum`, `namespace`, parameter properties or `import x =`. `declare module` augmentations are fine.
  - **Imports.** `verbatimModuleSyntax` is on: a type comes in with `import type`, and relative imports keep their `.ts`.
  - **No build step** for server code.
  - **Tests** go in `<package>/test/*.test.ts`, run by the root `pnpm test`.
  - **`@deepseek-ai/*` at runtime.**
    - `src/` imports them at runtime only from packages declared under both `peerDependencies` (`^0.2.0-rc.2`, cordis `~4.0.4`) and `devDependencies` (`0.2.0-rc.2`). For dish-gates, that is `@deepseek-ai/dsh-llm` (`createUserMessage`).
    - Everything else in `src/` is `import type`, including `dish-crew`, `dish-projects` and `dish-workspaces`.
  - **Services.**
    - Services a plugin doesn't `inject` are read with `ctx.get(name)` on each use, never by property. For dish-gates: `dishCrew`, `dishWorkspaces`, `dishProjects` and `shell`. For crew's row: `dishGates`, besides what it reads today.
    - dish-gates injects nothing, and waits for nothing with `ctx.inject`.
    - `apply` is synchronous: listeners are registered before anything could be awaited.
  - **Logs.** Each plugin logs as its name, and prints its own lines with dish-kit's `printOwnLogs` when its `terminal` row is true.
  - **The gate per task.** Every task ends with `pnpm typecheck && pnpm test` passing (the gate), and one commit with the message given.
- **The lockfile.**
  - Only Task 0 runs `pnpm install` and changes `pnpm-lock.yaml`. It declares every dependency later tasks need.
  - A later task that finds one missing stops and reports `NEEDS_CONTEXT`.
  - Every other task worktree runs `pnpm install --offline --frozen-lockfile`, with `pnpm_config_store_dir` set, before its gate.
- **The store-pin contract doesn't change.** No `storeDir` in `pnpm-workspace.yaml`, no store in `.npmrc`, and no store or `XDG_*` variable set by anything in this step.
- **The sandbox.**
  - A gate runs only through `ctx.shell`, with an explicit `sandboxPolicy: { mode: 'workspace-write', workspaceRoot: <clone> }`.
  - Never `danger-full-access`, never when `ctx.shell.sandboxMode` is undefined, and never as a retry after a sandbox failure.
  - No `child_process` import in `plugins/gates/src` (grep it).
- **dish's own git.** `git()` in `plugins/workspaces/src/git.ts` stays the only way dish's own code runs git.
  - dish-gates runs no git. It takes the worktree, the clone and their checks from `dishWorkspaces.resolve`.
  - Commands in the project's gate run inside the sandbox, as the coder's would.
- **Secrets.**
  - A gate's output is passed through `maskSecrets` before it is written to a log, the record or a steer.
  - `gateEnv` values are never logged, and are never put in a message or the record.
- **Paths.**
  - The worktree and the clone come only from `resolve`, which gives canonical paths.
  - A log path's parts are checked: owner, repo and slug are each one path segment of `[A-Za-z0-9._-]`, not `.` or `..` (a check of dish-gates' own: it imports no runtime code from dish-projects or dish-workspaces), and the child id is cut to `[A-Za-z0-9_-]`.
  - Logs are created new: `O_EXCL` and `O_NOFOLLOW`, directories 0700, files 0600.

## Review Focus

1. **A gate that runs outside the sandbox.**
   - Only `ctx.shell`, only with `mode: 'workspace-write'` and `workspaceRoot` the clone, and only when `sandboxMode` is set.
   - A runner failure is an `error`, never a retry.
   - No `child_process` in `plugins/gates/src`.
   - The real-shell tests show refused writes, with and without `dish-sandbox` (Tasks 5, 6).
2. **A gate that hangs, or leaves processes behind.**
   - The executor's timeout is at most 10 minutes.
   - The turn's signal and the plugin's (on dispose) both abort the gate.
   - The per-worktree lock waits only on a gate that is itself bounded.
   - The real-shell tests kill a grandchild on a timeout and on an abort. They find it by a unique argument in `/proc/*/cmdline`: a PID inside bwrap's namespace isn't the host's (Task 5).
3. **A gate result reaching the wrong child, or the wrong run.**
   - The listener uses only the payload's `agent`: its id for the record, and that agent for the steer.
   - Rounds are counted by `turn`.
   - `endRun` moves the results of the run in progress, and nothing else.
   - Tests: two coders gated at once, a follow-up's new turn, and a run that ends between two gates (Tasks 1, 6, 7).
4. **A record race.**
   - `addGate` is awaited inside `agent/turn-stopping`, before the turn can close, so it reaches crew's session queue before that run's `subagent/end`.
   - The plugin test drives the real crew host listeners in that order (Task 7).
5. **Stale gate state in crew or the judge.**
   - Crew's check reads the record through `lookup`, inside the session's lock.
   - It refuses while the reviewed coder runs.
   - The notice waits for `whenRecorded` as it does today.
   - The judge reads no gate state, and the steer never enters its task (Tasks 2, 3).
6. **A coder escaping its gate.**
   - An unresolvable worktree is `error` or `skipped`, never silence (correction 4).
   - The opt-out is recorded as `skipped`, and a review of it needs a ruling.
   - The command is always `projects.yaml`'s, read at each run, never the coder's (Tasks 3, 6).
7. **A loop, or a lost turn.**
   - A steer only after a `failed` result with `round < maxRounds`.
   - `error` and `skipped` never steer.
   - Step 4 stops a turn whose rounds are used up.
   - The listener never throws: a thrown listener fails the turn in dsh-agent-loop (Task 6).
8. **Secrets and paths.**
   - Masked output everywhere it goes.
   - `gateEnv` values never logged.
   - The log path's parts checked, and logs created without following a link (Tasks 4, 5).
9. **6b's contracts unchanged.** Grep the diff for changes under `plugins/workspaces/src` and `plugins/projects/src`. The only allowed one is the comment in `sweep.ts`. The `worktreeBrief` text without a gate is unchanged (Tasks 3, 8).

## Risks to watch

- **Gates run twice.** The coder's prompt and its skills tell it to run the gate before it finishes, and then the harness runs it again. That is up to 20 minutes for a 10-minute gate. Step 7 can drop the coder's own run once the notice is trusted.
- **A long gate holds the turn.** At worst a turn takes `maxRounds` × `gateTimeout`, 30 minutes. The coder counts as running all that time, and the writer limit (one by default) keeps another coder from starting.
- **The home directory is shared.** A gate's caches and installs land where the coder's do (sandbox-home's known limits: caches shared across workspaces, and things left in the home that run later outside the sandbox).
- **Dev.**
  - Without `DISH_SANDBOX_HOME=on` the home directory is read-only to a gate: a dev project points its caches into the clone with `gateEnv`.
  - With it on, dev's clones are inside the protected checkout and read-only, so gates can't write there at all.
- **The judge doesn't read the gate's message.** A coder's fix commands are judged against its brief, which covers its task. If the judge refuses fixes the brief doesn't name, the backlog item "read a bound coder's worktree block as part of its task" is the place to widen it, not the steer.
- **The final whole-branch review** (subagent-driven-development) sets `reviews` to some coder of the session, to pick the family. If that coder's last gate didn't pass, the review is refused until a ruling: pick a coder whose gate passed, or rule.
- **The closing text comes from `session/event`.** A message appended before dish-gates loaded is missed, which matters only for a turn that ends right after a reload. Then there is no opt-out, and the gate runs.
- **A coder can make its worktree unresolvable** with a refused key in `.git/config`. That is recorded as `error`, with the reason in the notice. The review then needs a ruling.
- **A restart mid-gate** records nothing for that run (open item 3).
- **dsh's `agent/turn-stopping` and `steer`** are relied on as dsh 0.2.0-rc.2 has them. The plugin test and the end-to-end run pin them. Re-check after a dsh upgrade.
