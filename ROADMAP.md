# Roadmap

The proposed build order for the system in [docs/design.md](docs/design.md). Each step gets its own spec when we start it.

| # | Step | Why here | Status |
|---|---|---|---|
| — | `copilot`: Copilot sign-in card, live model catalog | models | done |
| 1 | **Spike: specialist identity and keeping the chat open.** Can a delegated child get its role's prompt, tools and model? Does the main agent stay responsive while children work? | Everything else assumes yes. | done: yes to both, see the design doc's spike results |
| 2 | `dish-kit` + `config-store` ([spec](docs/specs/config-store.md)): XDG paths and the git-backed versioned config store. Move the Copilot cache to the XDG cache directory. | The foundation every plugin uses. | done: [plan](docs/plans/2026-09-30-config-store.md), pushing to `bketelsen/dish-config` |
| 3 | `prompts` ([spec](docs/specs/prompts.md)): role prompts in the config store, a persona row and a "dish" preset for the main agent, and Settings → Prompts (edit, preview, default diff and reset, history) | The first plugin on `config-store`, and small. | done: [plan](docs/plans/2026-10-01-prompts.md); the dish preset is the default for new chats |
| 3a | `skills` ([spec](docs/specs/skills.md)): dish's own skills, stored and versioned in the config store, edited in the web UI, offered to agents through dsh's skill mechanism. The pipeline's procedures (brainstorm, plan, test-first, review) live here. | `orchestrator` (7) runs on them; storage and editor can follow the `prompts` pattern. | done: [plan](docs/plans/2026-10-02-skills.md); checked end to end in a scratch dsh, deployed to the VM 2026-10-02 |
| 4 | `crew` ([spec](docs/specs/crew.md)): roles, model tiers, the cross-family reviewer rule, the `delegate` tool, the dish preset. Built on dsh-subagent directly, not dsh's experimental agent teams ([research](docs/research/2026-10-01-dsh-agent-team.md)). | Lets you talk to a delegating main agent. | done: [plan](docs/plans/2026-10-01-crew.md); live-checked delegation, the writer limit, the GPT reviewer, fix rounds and a restart |
| 4a | `judge` ([spec](docs/specs/judge.md)): Jev client and key card, a command gate on every shell call, the approval answerer (children included), screening web and MCP results for injected instructions, `ask_judge` for every agent, and Settings → Judge | Guardrails before anything runs unattended or in public. | done: [plan](docs/plans/2026-10-01-judge.md), installed and verified live 2026-10-01. Since [bketelsen/dish#11](https://github.com/bketelsen/dish/pull/11) (2026-10-03), a command the judge reads as read-only runs without the task check |
| 5 | **VM deployment** ([spec](docs/specs/deploy.md)): a Debian VM on Minideb from fleet (OpenTofu and Ansible), `dsh web` as a user service behind `tailscale serve`, dish's `deploy/` install script, the config store moved to the VM. Tailscale only; public access with GitHub sign-in is a later step. | Workspaces and triggers need to live where they'll run. | done: [plan](docs/plans/2026-10-01-deploy.md); running at `https://dish.<tailnet>.ts.net` since 2026-10-01 |
| 6a | `ops` ([spec](docs/specs/ops.md)): prod and dev, `update.sh` and `url.sh`, fleet back to provisioning. Also settings over the tailnet (`dish-web`) and the Copilot first sign-in card on a fresh profile. | dish working on itself needs dev data apart from prod's, the live checkout out of every chat, and deploys only by hand. | done: [plan](docs/plans/2026-10-02-ops.md); merged 2026-10-02 (`df9c4b1`) and rolled out the same day. Fleet's side is PR [bketelsen/fleet#38](https://github.com/bketelsen/fleet/pull/38) (fleet c5bb7f6), with a docs follow-up, [bketelsen/fleet#39](https://github.com/bketelsen/fleet/pull/39), both merged |
| 6a2 | `sandbox-home` ([spec](docs/specs/sandbox-home.md)): on the VM, an agent's sandboxed shell can write the home directory, less a protected list, through dsh's `runnerCommand` hook and `deploy/dish-sandbox`. It replaces most of mise approvals, which is shelved: the `dish-mise` wrapper and the judge's trusted rule and its checkbox stay unmerged on their branches, and its spec is only on the unpushed local branch `mise-approvals`. Fleet's part, the preinstalled toolchains and the trusted `~/work`, was kept, as [bketelsen/fleet#40](https://github.com/bketelsen/fleet/pull/40) and [bketelsen/fleet#41](https://github.com/bketelsen/fleet/pull/41). | Installs and caches failed with "Read-only file system" and needed an escalation, which the judge refuses for most of a crew child's. | done: merged as [bketelsen/dish#9](https://github.com/bketelsen/dish/pull/9) and deployed 2026-10-03; fleet's two PRs merged and applied the same day |
| 6b | `projects` + `workspaces` ([spec](docs/specs/projects-workspaces.md)): the repo registry and Settings → Projects, clones under `~/work` with onboarding, a read-only GitHub App for clones, setup, task worktrees with the `worktree` tool and `delegate`'s binding, the sweep, and the scratch workspace | Makes coding work safe: each project in its own workspace, each task in its own worktree. | done: [plan](docs/plans/2026-10-02-projects.md); merged as [bketelsen/dish#7](https://github.com/bketelsen/dish/pull/7) and deployed 2026-10-03, with [bketelsen/dish#10](https://github.com/bketelsen/dish/pull/10) (a worktree's setup runs in the sandbox). The VM uses dish's one App, `bketelsen-dish-dev` (no separate prod App was made; it got write access for step 7 on 2026-10-03). The chat test passed on `bketelsen/clippy`, and the squash-merge sweep check (the plan's rollout, step 8) was done on 2026-10-03 |
| 6c | `gates` ([spec](docs/specs/gates.md)): structural gates on the worktrees 6b binds | Makes coding work safe: the harness checks a coder's work. | done: [spec](docs/specs/gates.md), [plan](docs/plans/2026-10-03-gates.md); merged and deployed to the VM 2026-10-03 (built overnight while you slept: per-task reviews, two final reviews, one fix round); checked end to end in a scratch dsh |
| 7 | `orchestrator` ([spec](docs/specs/orchestrator.md)): runs owned by the project, a ledger per run written by the harness, structured reports for coders and reviewers, the ladder's last rung, `open_pr`, review feedback on a PR (`pr_feedback`, a reopened run), Settings → Runs. The dish preset stays with crew. | Plan → implement → gate → review → PR, end to end. | done: [spec](docs/specs/orchestrator.md), [plan](docs/plans/2026-10-03-orchestrator.md); merged as [bketelsen/dish#21](https://github.com/bketelsen/dish/pull/21) and deployed 2026-10-03, after a scratch end-to-end run. The first live run opened [bketelsen/clippy#13](https://github.com/bketelsen/clippy/pull/13), merged the same day |
| 7a | `browser` ([spec](docs/specs/browser.md)): a shared browser for agents and the user. One headless Chromium on the VM, outside the agent sandbox; a browser for each agent session, crew children included; ten `browser_*` tools for the main agent, the coder, the reviewer and the writer, whose page text the judge screens; a Browser tab with a live picture of the page that you can click and type into; and screenshots in the chat. It covers the backlog's dev-server previews: you see an agent's dev server in the Browser tab. | Agents could screenshot a page only in a command that can write, and only a dev server started in that same command; you couldn't see or steer what they saw. Asked for by the user. | done: [plan](docs/plans/2026-10-04-browser.md); merged as [bketelsen/dish#30](https://github.com/bketelsen/dish/pull/30) and deployed 2026-10-05, after an end-to-end run in a scratch dsh on the VM |
| 8 | `memory` + direction ([spec](docs/specs/memory.md)): the vault (pushed to the private `bketelsen/dish-vault`), with user memory for every chat and family memory keyed by projects.yaml's `family`, in Claude Code's auto-memory format (a `MEMORY.md` index, one file per memory); `remember` and `forget` for the main agent; the indexes loaded when an agent starts and after each compaction; each family's direction (`families/<family>/direction.md`) delivered to the agents working in its repos; Settings → Memory | The family chat (step 9) stands on it: a chat that lives for weeks works from its direction, its memory and the state of its runs, not its full history. It's useful at once in today's chats, since every project already names its family. Moved ahead of families on 2026-10-05, after comparing the plan with [Claude Code's Projects](https://code.claude.com/docs/en/claude-projects). | built on branch `memory`, [plan](docs/plans/2026-10-05-memory.md); reviewed and checked live in `pnpm dev` 2026-10-05 (the spec's Notes from the build); awaiting review and the rollout |
| 9 | `families`: a long-lived chat for each family that coordinates its runs, each run driven by its own main-agent session in the project's workspace (a spike first: can a plugin start a root session in another workspace and hear back when it ends?); the family's Overview, its runs grouped by state from harness facts (working, waiting on you, ready for review, landing, idle, resolved), with "Waiting on you" across families in place of a separate inbox; watching each run's PR (from the backlog); pausing a family. A family stays a set of repos, not a goal: its memory and direction cover every stream of work in its repos (2026-10-05). | Direction you can see and steer, and work you hand off in one place. | |
| 10 | `routines` (was `triggers`): approved prompts owned by a family, run on a schedule or a GitHub event (through Funnel). They replace initiatives (2026-10-05): standing work is a routine; one-off work is a run you start, or a suggested run you accept. The first routine is a weekly memory consolidation. Check dsh's `dsh-schedule` and `dsh-webhook-github` first. | Unattended work, only on what you approved. | |
| later | `copilot-usage`, `infra` (tiered approvals), `web-research` | | |
